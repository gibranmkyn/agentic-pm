# OKPS Trees

Teresa Torres' Opportunity Solution Tree (OST) is the gold standard for continuous discovery. OKPS is a small structural adjustment designed to integrate that same discipline into teams already operating on OKRs — solving three friction points that cause OST adoption to stall in practice.

The acronym: **Objective → Key Result → Problem → Solution**. The logic and discipline are the same as the OST; what changes is the vocabulary and the top-level structure.

**Author:** Aakash Gupta — Product Growth newsletter (2026). Practice built at Epic Games, Affirm, and Apollo.io. See [aakashg.com](https://www.aakashg.com).

---

## Structure

```
Objective (team's quarterly goal)
  └── Key Result (measurable outcome)
        └── Problem (unmet customer need or pain — from customer interviews)
              └── Solution (proposed product response — 2–4 per problem)
```

Compare to the OST:
```
Business Outcome
  └── Opportunity (unmet need — same as "Problem" above)
        └── Solution
              └── Assumption Test (explicit in OST; implied in OKPS)
```

---

## Why OKPS instead of OST

**Reason 1 — OKR integration.** Most teams already have OKRs. The OST runs as a parallel system with its own vocabulary ("business outcome," "opportunity"). OKPS plugs directly into the OKR framework teams already own — the Objective and Key Results come from the OKR cycle; you extend downward from there.

**Reason 2 — Vocabulary clarity.** In theory, "opportunities" (unmet needs) and "solutions" (product responses) are distinct. In practice, teams consistently write solutions where opportunities should go. "Problem" is closer to everyday language — harder to accidentally substitute a solution.

**Reason 3 — Stakeholder alignment.** Outcome-focused roadmapping is correct in principle but creates friction with executives who still expect to see outputs. OKPS shows the full chain: the outcome hierarchy (Objective → Key Result) and the proposed outputs (Solutions) beneath it. Both camps can read the same tree.

---

## How to apply it

1. **Start from your OKR.** Take the Key Result your team is owning this quarter. Don't create a new outcome — use the one you have.
2. **Map Problems.** For each Key Result, identify 5–7 customer problems that, if solved, would move the metric. Pull from customer interviews, support data, and session recordings — not brainstorming.
3. **Identify Solutions.** For each Problem, generate 2–4 possible solutions before committing to any one. The OST's "force 3–5 solutions" rule applies here too — don't fall into the one-idea funnel.
4. **Visualize.** Build the tree in FigJam, Miro, or Notion. The visual is the point — it makes the logic visible and reviewable.
5. **Review bi-weekly.** Add new Problems as interviews surface them. Retire Problems and Solutions that no longer apply.

---

## Common failure modes

| Failure | Fix |
|---|---|
| Starting from solutions already in the roadmap | Work backward: what Problem does this solution serve? If none in the tree, either add the Problem or question the Solution. |
| Problems that are actually solutions in disguise | Ask: "If we solved this, what customer experience would improve?" That experience is the Problem. |
| Building the tree once and filing it | The tree is a living artifact. Stale trees are worse than no tree — they anchor teams to outdated assumptions. |
| Skipping the multiple-solutions step | Don't put one Solution under each Problem. Generate 2–4 before committing. |

---

## When NOT to use it

- If your team doesn't use OKRs, the OST is simpler — OKPS's advantage is the OKR integration, which disappears if there's no OKR structure.
- If you need explicit Assumption Testing layers, use the OST — it makes assumption tests first-class citizens; OKPS leaves them to team discretion.
